Security and privacy

hippo reads agent transcripts, which are sensitive, and writes to files that agents load at the start of every session. This page says what it does with them. The full inventory (every hook, MCP tool, program hippo starts and host, kept in step with the code by a test) is Is it safe?.

When data leaves your machine

hippo’s own code makes no network calls: it has no HTTP client among its dependencies. The index, the records and the reports are local files. Data leaves your machine only through two kinds of child process that hippo starts.

A. The runners your roles use. By default every model call runs claude -p …, which sends the prompt to Anthropic under your own login. A runner can name another Claude account, or any CLI, which then decides where the prompt goes; hippo runners prints each role’s runner and its data domain, and fallback stays inside that domain unless you allow it. These commands call a model:

  • hippo dream, including --dry-run;
  • the lessons pass that follows dream (skip it with --no-lessons);
  • hippo lessons scan;
  • hippo ask, unless you pass --sources-only;
  • hippo add and hippo packs update, for the pack review;
  • hippo eval runs that use dreaming with a model (--with-model);
  • hippo doctor --model, which sends one word through each runner a role uses (--canary: a request to print two planted files);
  • the scheduled nightly dream.

B. Git over HTTPS, for packs. hippo add <url>, hippo add with --registry, hippo packs update, and hippo packs diff for a git-sourced pack fetch the pack with git.

Everything else is local: hippo and hippo start, detect, init, ingest, recall, ask --sources-only, fleet, resume, xray, incidents, context, brief, show, session, hook, hooks, guard, accept, config, log, review, revert, packs list and packs check, doctor without --model, and schedule.

The agent you run hippo inside. The Claude Code plugin’s start block and /hippo:ask and /hippo:day output, and the DeepSeek Harness and OpenCode plugins’ start blocks and their hippo_ask and hippo_day tool results, become part of that agent’s session, and the agent sends its session to its own model provider. hippo does not send them; the agent does, as with any file it reads. In Claude Code the commands run when you type them; in dsh the model calls the tools itself, and hippo_ask searches every indexed session, across projects. In OpenCode the start block is in the system prompt of every request of the session, and the model calls the tools itself too. Set either plugin’s tools: false to keep only the start block.

The text sent to a model is redacted index text. A note’s body is the exception: it is sent as written. Read the model command you run. The rest of this page assumes the default.

Redaction on ingest

Before any transcript text is indexed, hippo replaces matches of these patterns with [redacted:<kind>]. The whole match is replaced, including a key or header name in front of a secret.

KindWhat it matches
pemPEM private-key blocks
awsAWS access key ids (AKIA followed by 16 characters)
githubGitHub tokens (ghp_, gho_, ghu_, ghs_, ghr_, github_pat_)
providerAnthropic, OpenAI, Stripe, Slack and Google API key prefixes
jwtJSON Web Tokens
authAuthorization: headers: the word and the two words after it
kvA value of 16 or more characters after a key whose name contains secret, token, password, passwd, api_key or apikey, including quoted JSON keys and values
emailEmail addresses. A package specifier such as @scope/pkg@1.2.3 or react@18.3.1 is not an email
aadhaar12-digit Indian Aadhaar numbers. Digits inside a UUID are never matched
phoneIndian mobile numbers, with or without +91. Digits inside a UUID are never matched

Reasoning blocks of the model are never indexed. Tool calls and tool results are indexed, as text, after redaction. Every adapter ships with a test that plants a fake secret of each kind in a transcript and checks that none reaches the index.

Redaction is best-effort pattern matching. It will miss secrets that do not look like these patterns, and it will redact some harmless text: the aadhaar and phone patterns can still match some numeric ids. Text already in an index keeps the redaction it had when it was indexed. Do not rely on it as your only protection. The index is local and is never uploaded by hippo.

A derived Codex, dsh or OpenCode handoff is redacted in the same way, because it is transcript text written into a record you may commit. So is the handoff the Codex session-end hook takes from a Codex transcript.

The Codex hooks put the start block and the relevant notes into the Codex session, which Codex sends to the model provider it is set up with, as it does with every file the agent reads. They give the same text a Claude Code session gets from its hooks, and nothing from other projects.

What reaches a model, and how it is isolated

The commands in list A above run a model. A dreaming prompt contains:

  • the text of the notes the pass works on;
  • session records (ids, times, notes touched, handoffs);
  • transcript turns found in the index, already redacted;
  • text from reverted changes that a human confirmed.

The prompt marks each of these as untrusted data with <<<UNTRUSTED name>>> and <<<END name>>> lines, and the shipped prompts and personas tell the model to ignore instructions inside. That reduces prompt injection through transcript text; it does not make it impossible.

The reviewer receives only its persona (as the system prompt), the note, the proposed change and the evidence turns. It does not receive the proposer’s reasoning or stated reason.

Each model run:

  • starts in its own new, empty folder, $HIPPO_HOME/model-runs/<ulid>/ (mode 0700), which is removed when the run ends, so two runs at once never see each other’s files; a run that starts removes folders older than a day, which only a crashed run leaves;
  • with the default runner, runs claude with no tools, no settings files, no MCP servers and no saved session, so the model can read nothing on your disk and leaves no transcript. hippo doctor --model --canary checks that a runner cannot read a planted file in its run folder or in $HIPPO_HOME;
  • runs inside an OS sandbox where the machine has one (sandbox-exec on macOS, bwrap on Linux): the CLI can read its run folder, its install and its account folder (for Claude Code also ~/.claude.json and the macOS login keychain it signs in with), not the rest of your home folder, $HIPPO_HOME or the workspace, and it can write only its run folder, its account folder and the system’s temporary folders. Network is allowed. The account folder holds the CLI’s own credentials, which is why a runner that may have tools cannot write notes, receipts or lessons without allow_tools, and why a reviewer’s notes and a proposal’s reason are redacted and cut to 2,000 characters before they are written. The sandbox narrows what injected text can make a CLI read; it is not a security boundary;
  • gets a limited environment: a base list (PATH, HOME, locale, terminal, proxy and certificate variables), TMPDIR set to the run folder, the sign-in variables of its preset, and the runner’s env_pass. A credential in the shell that started hippo does not reach it;
  • is stopped after 600 seconds;
  • receives transcript text on standard input, not in its arguments, so it does not show in the process list.

The exception is a configuration that still sets model_command or reviewer_command_override: those commands run as before 0.5.0, with hippo’s whole environment and no sandbox, so an existing setup keeps working, and their isolation is the command’s own job. hippo runners migrate turns them into runners. Where a machine has no sandbox (hippo runners says which), claude still runs, with no tools as before, and a command runner may serve propose, review or lessons only with allow_unsandboxed = true.

Which provider sees which call is the runners your roles use: hippo runners prints each role’s runner and data domain, and a fallback never leaves that domain unless [fallback] cross_domain names the role.

The guard

The guard runs hippo guard check in an agent’s pre-tool hook before each tool call it covers (shell commands, file reads and writes, fetches, and in Claude Code MCP tools). It reads the call, compares it with rules, and answers in the agent’s format. It is machine-wide: hippo guard install puts it in every Claude Code account’s user settings.json (with --agent gemini in Gemini CLI’s ~/.gemini/settings.json, with --agent codex in Codex’s $CODEX_HOME/hooks.json, where Codex asks you to trust it at its next start, and with --agent cursor in Cursor’s ~/.cursor/hooks.json), never in a workspace’s committed settings, so a session in a repository cloned into ~/Downloads is checked too. The dsh and OpenCode plugins run it with guard: true. cursor-agent also runs the Claude Code entry in ~/.claude/settings.json; with Cursor’s own entry installed, that one stays quiet for Cursor’s calls so each is checked once (Limits).

Warn-only in 0.6.0. Every rule warns, whatever its configured action: the call runs, the agent gets a note to tell you, and the call is logged. Where the warning shows, checked by running each agent (scripts/agent-e2e): Claude Code gives it to the model after the result and shows it to you; Codex gives it to the model and its TUI shows it to you (codex exec does not); Cursor gives it to the model only; OpenCode puts it at the top of the call’s result, which you see in the tool’s output; dsh gives it to the model with the result and keeps it in the session (its headless profile prints only the final answer); Gemini CLI shows it to you and cannot give it to the model. Only the self-protection rules below refuse a call. ask and block take effect in a later release, once hippo guard test counts on real history show which defaults are quiet enough.

What it looks for. The built-in kinds are those of the incidents: remote-script (a download piped into an interpreter), fresh-clone-exec (a repository’s install or build run soon after it was cloned, in the same call or, read from the disk, in a later one), credential-read and guard-bypass. Rules in a note add match rules (a regular expression over a shell command) and path rules (a glob over a file tool’s paths), raise a kind’s action, or add allow entries (hosts for remote-script, clone origins for fresh-clone-exec). For one call the strictest action wins; an allow entry never silences a match rule.

Where rules come from. Four layers, compiled into $HIPPO_HOME/guard/compiled.json: hippo’s built-ins; your machine rules in $HIPPO_HOME/guard/machine.toml; the team’s guard note (guard_note, <notes_dir>/Guard.md by default: only its fenced hippo-guard blocks are read), for sessions inside the workspace or one of its worktrees; and packs’ Guard.md, which can add rules and raise actions but never add allow entries. Dreaming and hippo lessons keep never write the guard note.

Self-protection. Built-in rules no note can lower refuse an agent’s call to hippo accept, hippo guard accept, guard allow, guard uninstall, hippo hooks uninstall, hippo lessons share, and hippo config set|unset of a key in the accept table or share_lessons; and an agent’s write (by a file tool, or a shell redirect, cp, mv, tee, sed -i and the like) under $HIPPO_HOME/guard/, $HIPPO_HOME/accepted/ or to $HIPPO_HOME/config.toml. Only this install’s real files count: the hook’s own $HIPPO_HOME and ~/.hippo, by their real paths. A path built from a variable ($HIPPO_HOME in an agent’s script, whose value the guard cannot know) or a ~ in a script that sets HOME itself does not, so an agent testing hippo in a scratch home is not stopped. An agent never needs to accept a loosening for you, so these never stop legitimate work.

When the guard fails. If hippo is missing, crashes, or does not answer within [guard] timeout_ms (2,000 by default), the call proceeds and the failure is logged in $HIPPO_HOME/guard/failures.jsonl; hippo doctor counts the last day’s. With [guard] fail = "closed" the call is refused instead: the guard’s own watchdog refuses a slow call, Claude Code’s hook entry gets onFailure: "block" for a missing or crashing hippo (run hippo guard install --yes after changing fail; doctor says when the two differ), and the plugins read fail themselves. Gemini CLI and Codex have no such setting, so a missing hippo there fails open.

What it keeps. A call that matches a rule is a line in $HIPPO_HOME/guard/log.jsonl (0600): time, agent, session, tool, rules, decision and the command after redaction, cut to 400 characters. Other calls only add to a per-day count. The compiled rules hold no transcript text. The answer goes to the agent, and so to its model provider, as any tool result does; it quotes only a host or path made of plain characters, otherwise (host not shown).

It is not a security boundary. It reads a call’s text, not what the call does. A script written to a file and then run, a command decoded from base64, or an edit through a language runtime pass unseen, and anything that controls the machine can remove the hook. It makes the common agent paths to these mistakes visible, and the injected-by-text case fail visibly.

The accept rule

Shared settings in .hippo/hippo.toml have many writers: every teammate with push access, and every agent that can edit files in the workspace. So a setting that makes hippo stricter applies at once, and one that makes it looser waits until you accept it on your machine.

SettingApplies at onceWaits for hippo accept
The guard rule set, from every layera rule added; an action raised; an allow entry removedan allow entry added; an action lowered; a rule removed; any edit to a match rule (a removal and an addition)
guard_noteany change
[guard] failopen → closedclosed → open
[guard] timeout_msany change
[team] inboxshared → locallocal → shared
min_hippo_versionraisedlowered

Each machine keeps what it accepted in $HIPPO_HOME/accepted/<workspace-id>.toml (0600), with the hash of the guard rules in force. Until you accept, the value you accepted last stays in force, and doctor’s accept row, hippo accept --list, and Hippo.app (Manage › Health) say “loosening waiting”. A workspace you just cloned starts from the defaults, so its loosenings wait too.

To accept, use Hippo.app’s Accept… on the accept row (a native dialog that shows each change), or run hippo accept yourself: it shows the same list and asks. It needs a terminal on stdin and stdout and refuses when an agent’s marker is set in its environment (Claude Code, Codex, OpenCode, Gemini CLI, Cursor and others set one in the commands they run); there is no --yes. dsh, Muse and Command Code set no marker hippo knows, so there only the terminal check applies. An agent with a shell runs as you and can get around all of this; the rule stops the casual and the injected-by-text cases and leaves a trace in the transcript (guard-bypass). hippo config set of a setting in the table also raises min_hippo_version to 0.6.0, so a teammate’s older hippo refuses to write rather than ignore it.

What limits a write

Dreaming can only change a note through one code path, and that path needs a receipt from a reviewer’s confirmation:

  • Every proposal is checked before review: the note must be a visible .md file inside notes_dir (symbolic links are resolved and must still lead there), the evidence must exist in the index, and a replace must quote evidence word for word and may not exceed half the note.
  • A write happens only if the note is byte-identical to what went into the prompt.
  • Before the write, the note is copied to .hippo/snapshots/. hippo revert restores it.
  • hippo revert refuses a receipt that is not an applied confirmation, a snapshot outside .hippo/snapshots/, or a snapshot whose hash does not match.

A confirmed change is still a model’s work, reviewed by a model. Read the reports.

Pass and persona files are text, and hippo never executes anything a pack contains. The loader refuses symbolic links, files over 64 KiB and duplicate pass names, so a pack cannot point the model at a file elsewhere on your disk.

Everything hippo creates under $HIPPO_HOME is private: folders 0700, files 0600, the index included. hippo runs with a umask of 077, so files it writes elsewhere (notes, .hippo/ records, hook files) are created 0600 too; a file that exists keeps its mode. A command that finds $HIPPO_HOME itself open to other accounts makes it 0700 and says so once; hippo doctor lists anything inside still readable by others, and hippo doctor --fix-permissions tightens it.

Proposals, receipts, review marks, pack reviews and lessons carry hippo_version, the version of the hippo that wrote them. A workspace’s hippo.toml can set min_hippo_version: an older hippo then refuses to write notes or records there, or to call a model for it, and so does a hippo that finds keys in hippo.toml it does not know (Configuration). | <workspace>/.hippo/ | Settings, the core pack, session records, proposals, receipts, reports, dream state; snapshots/ is gitignored | | <notes_dir>/ | Your notes, changed only by confirmed dreaming changes or by you | | log_path | The generated session log | | ~/Library/LaunchAgents/ | The two job files, on macOS, if you run hippo schedule install. Elsewhere it writes nothing |

Session records, proposals and reports can hold note text, handoffs and quoted transcript text. If you commit .hippo/ to a shared repository, treat it as you would the notes.

Reporting a vulnerability

Use GitHub’s private vulnerability reporting on the hippo repository (the Security tab, then “Report a vulnerability”). Do not open a public issue for a security problem. You get an acknowledgement within three days. Confirmed issues are fixed before public discussion, and reporters are credited unless they prefer not to be.

In scope: anything that gets secrets or personal data past redaction into the index, anything that lets dreaming write without a recorded review, and anything that lets a pass read or write outside its declared permissions. Vulnerabilities in the agents themselves, such as Claude Code or Codex, belong to their vendors.
